## 1. Executive summary

Eleven prototype scripts ran from a fresh synthetic seed in one reproducible run:

- 10 prototypes plus the late-data scenario.
- **161 of 161 checks passed**, exit code 0.

Every destructive path ended in one of two ways:

- **exactly the verified, unchanged candidate rows were deleted**, or
- **0 rows were deleted**.

| # | Prototype | Checks | Result |
|---|---|---|---|
| P1 | Exact candidate freezing | 15/15 | Passed |
| P2 | Whole-day target logic (124,999 + 210 = 125,209) | 17/17 | Passed |
| P3 | Multi-table / FK dependencies | 23/23 | Passed |
| P4 | Archive format comparison | 4/4 | Passed (Parquet shown lossy with a typical JS mapping) |
| P5 | Archive verification under corruption | 12/12 | Passed (8/8 corruptions → DELETE = 0) |
| P6 | Delete batch performance | 9/9 | Passed |
| P7 | Failure / resume at 10 crash points | 37/37 | Passed |
| P8 | Schema change during a job | 9/9 | Passed |
| P9 | RLS / least-privilege archiver role | 18/18 | Passed (local image; hosted unconfirmed) |
| P10 | Database storage after DELETE | 8/8 | Passed |
| §13 | Late / backdated records during a job | 9/9 | Passed |

**Where the evidence changes the Phase 2 architecture:**

1. **The row fingerprint alone does not detect schema drift.** Rename, type change, constraint and FK changes leave every fingerprint intact. **A schema hash check before deletion is mandatory** (P8).
2. **Whole-day selection must run inside the freeze snapshot**, not before it. Otherwise concurrent inserts make day totals and frozen rows disagree (late-data variant A).
3. **The restore-and-fingerprint check (V8) must be part of the deletion gate, not sampled.** It was the only check that caught a consistently re-hashed altered row, and costs ~1 s per 125k rows (P5).
4. **RLS silently hides rows from a non-bypass role.** Even the post-deletion reconciliation is blind. Only a catalog-level preflight catches it (P9).
5. **An explicit plain `VACUUM` after each job** is needed for predictable space reuse. Autovacuum timing varied between runs (P10).
6. **The deleter must own its transaction.** A nested `BEGIN` silently committed the caller's transaction in the test harness (P5). A guard now refuses nested use.

**Not tested (hosted-only; user decision to skip):**

- Supavisor session mode with a custom role
- hosted read-only enforcement
- BYPASSRLS on the hosted platform
- real Nano CPU timing
- egress metering

Real object storage (ADR P-7) and the real application schemas (ADR P-5) were also out of scope.

## 3. Results

### P1 — Exact candidate freezing

- **Objective:** Prove deletion removes only frozen, unchanged rows (ADR D-01, D-03, invariant I-1).
- **Setup:** RosiFit `attendance_records`, date column `attendance_date`, time zone `Asia/Kolkata`, cutoff 2025-09-30, target 5,000.
- **Test:**
  1. Whole-day selection.
  2. Freeze + export in one `REPEATABLE READ READ ONLY` snapshot, writing `data/*.csv.gz` plus `keys/*.csv.gz` with (PK, `sha256(row::text)`).
  3. Verify V1–V8.
  4. Then, as the application: edit one frozen row, delete one frozen row, insert a new row dated on the boundary day, and insert a backdated row 30 days before the first archived day.
  5. Delete in batches of 2,000 by exact PK + fingerprint.
- **Result:**

| Row | Outcome |
|---|---|
| Unchanged frozen rows | **Deleted** (5,056) |
| Changed row | **Not deleted** — counted as drifted (1) |
| Row deleted by the app | Counted as **missing** (1) |
| New in-range row | **Preserved** |
| Backdated row | **Preserved** |

  Reconciliation holds: 5,058 requested = 5,056 deleted + 1 drifted + 1 missing.
- **Counterfactual:** a naive `DELETE … WHERE attendance_date < boundary+1` (run in a rolled-back transaction) would have removed 5,059 rows, including the unarchived new row, the backdated row and the stale edited row.
- **Measurements:**
  - Selection: 4,959 + final day 99 = 5,058.
  - Export 599 ms; delete 122 ms.
  - Fingerprinting 994,945 rows: SHA-256 **11.6 s** vs MD5 **12.0 s** (no material difference).
- **Fingerprint stability:** deterministic for unchanged rows. **Changes when the session `TimeZone` changes** (timestamptz text), so session settings must be pinned. They are pinned in `db.ts` and recorded in the manifest.
- **Conclusion:** The exact-PK + fingerprint model works as designed. Use **SHA-256**.

### P2 — Whole-day target logic

- **Objective:** Validate the documented rule, unchanged, including the worked example.
- **Setup:** Three independent tables with different date types:
  - `timestamptz` event time
  - `date`
  - `timestamptz` created time

  Days 2025-05-01 → 2025-07-30 total exactly 124,999, with three zero-row days. July 31 has A = 60, B = 70, C = 80. August has more rows. 666 NULL-date rows. Time-zone edge rows at **23:59:59 IST July 31** and **00:00:00 IST Aug 1**.
- **Test:** Per-day aggregation in `Asia/Kolkata` → the **Phase 1 `selectWholeDays()` unchanged** → freeze in one snapshot. Plus pure-function edge cases.
- **Result:**
  - Before the final day: **124,999**. Final day 2025-07-31 = **210** (60/70/80). Selection = **125,209**.
  - Frozen set = **125,209**. **All 210 July 31 rows frozen; 0 August 1 rows.**
  - NULL dates never enter any day. Zero-row days are simply absent.
  - Edge cases:

| Case | Outcome |
|---|---|
| Exact hit | Stops that day (125,000) |
| Crossed | Whole final day |
| Never reached | `reachedTarget=false`; no job decided here (ADR §3.10 remains UNDECIDED) |
| One day > target | That whole day only (300,000) |
| Explicit zero days | Harmless |
| Unordered input | Processed ascending |

- **Measurement:** grouping by **UTC** day would put **61** table-A rows on July 31 instead of 60. The 00:00 IST Aug 1 row falls on July 31 in UTC.
- **Conclusion:** Rule confirmed exactly. **The business time zone must be pinned per application** (ADR §3.6 remains a business input).

### P3 — Multi-table / FK dependencies

- **Objective:** Discover the graph programmatically, derive order, block unsafe selections (ADR D-08).
- **Setup:**
  - Jalsa `orders ← order_items (NO ACTION)`, `orders ← payments (RESTRICT)`.
  - Lab schema with CASCADE, SET NULL, a two-table cycle and a self-reference.
- **Result (all from `pg_constraint`, nothing hard-coded):**

| Selection | Outcome |
|---|---|
| Parent + both children | No blocking issues. **Derived** delete order: `order_items, payments → orders`. |
| Parent without children | Blocked (2 edges). If forced, Postgres rejects with 23503, i.e. fails closed. |
| Child without parent | Allowed, with a warning. |
| CASCADE / SET NULL child unselected | Blocked. Demonstrated in a rolled-back transaction: deleting 10 parents **silently deleted 30 children and nulled 19 notes**. |
| Cycles | Two-table cycle and self-reference both detected; delete order refuses. |
| Unrelated table in a root-driven group (`audit_logs`) | Rejected ("archive as its own group"). |

  **Root-driven group end-to-end:** 3,055 rows (611 orders, 1,833 items, 611 payments). A late-night order at 23:58 IST on the boundary day kept its 3 next-day items and its payment in the same freeze. **Per-table date selection would have split it.** An order that gained a new item after the freeze was **held, not deleted, with no FK error**; the new item was preserved; **0 orphans**.
- **Conclusion:** ADR §5 confirmed. Two refinements for Phase 3B:
  - The guard "do not delete a row still referenced by any row" makes late children safe without FK errors.
  - FK column arrays must be cast to `text[]`. The driver does not parse `name[]`; a first-run bug caught by the test.

### P4 — Archive format

- **Objective:** Compare formats on size, speed and restore fidelity (ADR D-12).
- **Setup:**
  - "Fidelity" table (100,000 rows): `numeric(20,6)`, unconstrained `numeric` incl. `NaN`, `float8` incl. `Infinity`, microsecond `timestamptz`/`timestamp`, `date`, `boolean`, `uuid`, `jsonb` (incl. the integer 9007199254740993), `text[]` with commas/quotes/NULL, `bytea`, Unicode (Hindi, Tamil, Arabic, emoji, zero-width), 60 KB texts in 1 % of rows, empty string vs NULL, `interval`.
  - "Narrow" table (750,000 order-item-like rows).
- **Fidelity test:** restore into an identical table; compare **every column** with `IS DISTINCT FROM`.
- **Results (0.5 CPU):**

| Format | Table | Size | Export | Restore | Fidelity |
|---|---|---|---|---|---|
| **CSV.GZ** (`COPY … CSV`) | fidelity 100k | 7.99 MB | 1.4 s | 3.4 s | **Exact, all 15 columns** |
| JSONL.GZ (`row_to_json`) | fidelity 100k | 8.44 MB | 2.5 s | 23.7 s | Exact (restored by Postgres, not by JS `JSON.parse`) |
| Parquet (hyparquet, basic typed mapping) | fidelity 100k | 9.54 MB | 5.2 s | 6.2 s | **Lossy**: `numeric` (98,970 + 66,666 rows), µs timestamps (99,900 + 100,000), `jsonb` big integer (100,000) |
| XLSX (exceljs) | fidelity 100k | 15.3 MB | 7.6 s | n/a | **1,000 cells exceed Excel's 32,767-char limit** |
| **CSV.GZ** | narrow 750k | 9.03 MB | 1.2 s | 1.9 s | Exact |
| JSONL.GZ | narrow 750k | 10.3 MB | 3.1 s | 18.5 s | Exact |
| Parquet | narrow 750k | 9.02 MB | 6.2 s | 10.7 s | Exact (no µs / big numerics in this table) |
| XLSX | narrow 750k | 28.1 MB | 10.8 s | n/a | Row limit 1,048,576; not archival |

- **Conclusion:**
  - **CSV.GZ via Postgres `COPY` confirmed as the archive format.** Exact, smallest or near-smallest, fastest both ways.
  - Parquet can be exact only with explicit DECIMAL / TIMESTAMP_MICROS / string mappings, which is extra complexity for no size gain here.
  - JSONL is exact but ~7–10× slower to restore, and loses big integers if any JavaScript code parses it.
  - XLSX is confirmed as human-facing only.
- **Side note:** the npm package `@dsnp/parquetjs@1.9.3` was published without its compiled code (unusable). This is a reminder to pin and vet worker dependencies.

### P5 — Archive verification

- **Objective:** Determine which checks are required. Every corruption must yield VERIFICATION FAILED → DELETE = 0 (ADR §10).
- **Setup:** 125,152-row attendance archive (whole days to 2024-05-09). Expected values come from the **control-plane record written at export time**, not only from files stored beside the archive.
- **Checks:**

| Check | Covers |
|---|---|
| V1 | Objects exist; sizes match |
| V2 | SHA-256 of manifest and files = control-plane record |
| V3 | Gunzip + CSV parse |
| V4 | Row counts |
| V5 | PK set data = keys, no duplicates |
| V6 | Manifest counts, schema hash and boundary = control plane; Σ day totals = Σ rows |
| V8 | Restore into a scratch DB with the archived column types; every row's fingerprint = keys |

- **Corruption matrix (all → `passed=false`, deleted = 0; source row count unchanged):**

| Corruption | Caught by |
|---|---|
| 1. Flipped bytes inside `data.csv.gz` | V2b, V3 |
| 2. Wrong checksum recorded | V2b |
| 3. One row removed, archive re-gzipped **and re-hashed consistently** | V4, V5, V8 |
| **4. One value altered, re-gzipped and re-hashed consistently** | **V8 only** |
| 4b. One value altered, checksums not updated | V1b, V2b, V8 |
| 5. Manifest boundary edited | V2a, V6c |
| 5b. Manifest row count edited **and** control-plane hash re-recorded | V6a, V6d |
| 6. Keys file missing | V1 |

- **Pristine archive:** gate opens, and exactly the 125,152 frozen rows were deleted. This was a real committed delete of synthetic rows. An earlier harness revision mislabelled it a "dry run"; see finding F6.
- **Measurements (125k rows):**
  - export 1.8 s
  - V1–V6 **1.0 s**
  - V1–V8 **2.0 s**
  - data 1.85 MB; **keys 4.85 MB** (hex SHA-256 does not compress)
- **Conclusion:**
  - V1–V6 **and V8 are all required on every job**. V8 is the only defence against content that was wrong when first hashed (serialization bugs, a consistent rewrite) and costs ~1 s per 125k rows.
  - Checksum authority must be the control plane.
  - Keys should store the fingerprint compactly (binary, or base64 of 32 bytes) to cut archive size.

### P6 — Delete performance

- **Objective:** Find a conservative, retry-safe batch size (ADR §11).
- **Setup:** Copy of 869,793 attendance rows (90 MB), 50,000 frozen rows per batch size.
  - Exact PK + fingerprint delete.
  - One transaction per batch: `lock_timeout` 2 s, `statement_timeout` 30 s.
  - A **concurrent synthetic app** continuously updated random rows *in the same slice* and inserted new rows.
- **Results:**

| Batch | Rows/s | Txn p50 | Txn p95 | Txn max | WAL/batch | App latency p95 | App max |
|---|---|---|---|---|---|---|---|
| 500 | 35,920 | 8 ms | 52 ms | 76 ms | 58 KB | 45 ms | 66 ms |
| 1,000 | 46,376 | 12 ms | 57 ms | 61 ms | 113 KB | 45 ms | 47 ms |
| **2,000** | 60,846 | 18 ms | 68 ms | 98 ms | 164 KB | 53 ms | 82 ms |
| 5,000 | 75,576 | 77 ms | 138 ms | 138 ms | 357 KB | 62 ms | 87 ms |
| 10,000 | 20,828 | 480 ms | 570 ms | 570 ms | 715 KB | 55 ms | 215 ms |

- **Failure injection:**
  - A batch hitting an app-held row lock failed with **55P03 after 2.0 s** and rolled back completely (0 of 2,000 deleted).
  - The retry after release deleted all 2,000.
  - Re-running the committed batch deleted **0** (idempotent).
- **Guard cost:** 10,000 rows took 28 ms by PK only vs 483 ms with the fingerprint (~48 µs/row). Acceptable for safety.
- **Conclusion:**
  - **Default 2,000** (the Phase 1 default) is confirmed as conservative: sub-100 ms transactions and no visible app impact.
  - **5,000 as an upper bound.**
  - **10,000 is unsafe here:** throughput collapses and transactions reach ~0.5 s.
  - Re-measure on hosted Nano before production.

### P7 — Failure / resume

- **Objective:** Safe resume and idempotency at every step (ADR §12).
- **Setup:** Job runner over the control-plane tables:
  - leases + heartbeats
  - per-step checkpoints
  - attempt-scoped export prefixes
  - `job_batches` with `started` / `done` markers
  - unique partial index "one active job per (application, table group)"
  - kill switch

  Jalsa root-driven group (orders + items + payments), target 3,000, batch 100 root rows.
- **Test:** For each crash point, crash worker A, then:
  - try a duplicate job (must be rejected),
  - try worker B while the lease is valid (must be blocked),
  - expire the lease, resume with worker B (approve when needed),
  - reconcile.
- **Result (every row passed all checks):**

| Crash point | State at crash | Rows deleted at crash | Resume action | Export attempts | Retried-batch "missing" | Final |
|---|---|---|---|---|---|---|
| before export | exporting | 0 | export | 1 | 0 | completed |
| during export (after 1st table) | exporting | 0 | **new attempt**, partial discarded | 2 | 0 | completed |
| after export, before checkpoint | exporting | 0 | new attempt | 2 | 0 | completed |
| after upload checkpoint | verifying | 0 | verify | 1 | 0 | completed |
| during verification | verifying | 0 | re-verify | 1 | 0 | completed |
| immediately before deletion | deleting | 0 | delete from batch 0 | 1 | 0 | completed |
| **mid-deletion, connection dropped inside txn** | deleting | 1,500 (3 committed batches) | in-flight batch was **rolled back by the server**; re-run | 1 | 0 | completed |
| **mid-deletion, after commit, before checkpoint** | deleting | 2,000 | re-run batch finds its 500 rows gone → counted `missing` on a retried batch | 1 | 500 | completed |
| immediately after deletion | deleting | all | skip done batches → verify | 1 | 0 | completed |
| during deletion verification | verifying_deletion | all | re-verify | 1 | 0 | completed |

  In every scenario:
  - the duplicate job was rejected (23505),
  - the second worker was blocked by the lease,
  - every table reconciled (`requested = deleted + skipped + missing`, and rows still present = skipped),
  - **0 orphans**,
  - rows removed from the DB = rows reported deleted + rows attributed to the crashed attempt.

  Also:
  - **Kill switch** on → job stops in `requires_review` with **0 deleted**.
  - **Nested-transaction guard** → `deleteBatch` inside a caller's transaction is refused, 0 deleted.
- **Operator action required:** none for any crash point. Resume is automatic after lease expiry.
- **Conclusion:** ADR §12 mechanics confirmed. One limitation: "missing" rows on a retried batch are *attributed* to the crashed attempt. An app deleting the same row in that window would be indistinguishable. This is harmless to safety, but affects reporting precision.

### P8 — Schema change

- **Objective:** Schema drift must never let a stale archive drive deletion.
- **Setup:** Six scratch tables (20k rows each). For each: job → `ready_for_deletion` → DDL → approve → run.
- **Result:**

| Change | Job outcome | Rows deleted | Would the row fingerprint alone still delete? |
|---|---|---|---|
| Added column | requires_review | 0 | No (0 of 5,235 match) |
| Removed column | requires_review | 0 | No (0) |
| **Renamed column** | requires_review | 0 | **Yes — all 5,235** |
| **Type change int → bigint** | requires_review | 0 | **Yes — all 5,235** |
| **New CHECK constraint** | requires_review | 0 | **Yes — all 5,235** |
| **New FK with ON DELETE CASCADE** | requires_review | 0 | **Yes — all 5,235** |

  All six were detected by the **schema/graph hash** comparison before deletion.

  DDL arriving **during** an open export snapshot:
  - with `lock_timeout` 1 s → fails fast (55P03);
  - without `lock_timeout`, the waiting `ALTER TABLE` **blocked an ordinary application read** until its 2 s timeout (57014).
- **Conclusion:**
  - The ADR's assumption A-2 ("schema change → all rows drift → fail-closed") is **only true for added/removed columns**.
  - The schema hash (columns, types, constraints, triggers, RLS) is **mandatory**.
  - Keep exports short, and have application migrations use `lock_timeout`.

### P9 — RLS / archiver role

- **Objective:** Least privilege, and whether RLS can hide candidate rows (ADR §16.2, P-6).
- **Setup:** Role `uniqbotz_archiver`: `LOGIN NOINHERIT CONNECTION LIMIT 2`, role-level `statement_timeout 10min`, `lock_timeout 2s`, `SELECT, DELETE` on one table only. Created by `postgres`, which is non-superuser as on hosted.
- **Result:**

| Test | Outcome |
|---|---|
| Role-level timeouts | Applied on login |
| Full visibility without RLS | Yes |
| INSERT / UPDATE / TRUNCATE / ALTER | 42501 |
| Unrelated table SELECT / DELETE | 42501 |
| `CREATE ROLE` | 42501 |
| Catalog introspection (planning) | Works |
| Export + exact delete | **Works with only SELECT + DELETE** (1,501 rows) |

  **RLS:**
  - A `USING (member_id % 2 = 0)` policy **silently** showed the archiver 9,493 of 18,968 rows, with no error. The catalog estimate still said 20,000.
  - A candidate for the same days would contain **1,024 rows instead of 2,061**, so whole days are no longer whole.
  - With policies only for the `authenticated` role, the archiver sees **0 rows**.
  - The preflight check (`relrowsecurity` from `pg_class`) **blocks the job**.
  - A role created **with `BYPASSRLS` by `postgres` works on the image**, sees all 18,968 rows, and still cannot UPDATE.
- **Conclusion:** A catalog-level RLS preflight is **mandatory**. The post-deletion reconciliation runs as the same role and is equally blind.
  - Use a BYPASSRLS archiver role, *or* explicit per-role policies. **Must be confirmed on hosted Supabase.**
  - Refinement: the prototype currently blocks *any* RLS-enabled table. Phase 3B should allow it when the role has `rolbypassrls`.
  - The `auth` schema is not present in this image, so "no access to auth.users" was not testable locally.

### P10 — Database storage after DELETE

- **Objective:** Actual space behaviour (ADR §7.4). Run in a **dedicated** database created for this experiment.
- **Result (600,000 rows; archive-style delete of 125,000; size series in `results/p10-storage.json`):**

| Step | Database | Heap | Indexes | Dead tuples |
|---|---|---|---|---|
| Baseline | 61.9 MB | 37.5 MB | 17.0 MB | 0 |
| Right after deleting 125k | **61.9 MB** | 37.5 MB | 17.0 MB | 125,000 |
| After autovacuum (fired within 5 s) | 61.9 MB | 37.5 MB | 17.0 MB | 0 |
| After explicit `VACUUM` (94 ms) | 61.9 MB | 37.5 MB | 17.0 MB | 0 |
| After re-inserting 125k new rows | 65.4 MB | **37.5 MB (reused)** | 20.4 MB | 0 |
| Same 125k inserts into a fresh table | +7.2 MB | | | |
| Another 200k deleted + VACUUM, then **VACUUM FULL** | 65.4 → **43.1 MB** | 37.5 → 24.3 MB | 20.4 → 11.3 MB | |

  Other measurements:
  - The delete wrote **11.5 MB of WAL**. WAL counts toward disk, not database size, on Supabase (ADR §7.1).
  - VACUUM FULL took 1.15 s, and ordinary reads waited through it (89 ms → 1,053 ms).
  - **Read-only mode** (`default_transaction_read_only = on`, the mechanism Supabase documents): the archiver's DELETE fails with **25006**. The documented `SET SESSION CHARACTERISTICS … READ WRITE` escape works **for any role**.
  - **Earlier run of the same script (before restructuring):** autovacuum fired *during* the delete and left **76,180 dead tuples** unprocessed, and re-inserting 125k rows then grew the heap by **3.1 MB**. Space reuse depends on vacuum timing.
- **Conclusion:**
  - DELETE never shrinks the database.
  - Freed space is reused only after vacuum.
  - **Run an explicit plain `VACUUM (ANALYZE)` on each table after a job** (cheap, no exclusive lock).
  - VACUUM FULL reclaims space but blocks the table. It must remain a manual, scheduled operation.
  - The worker must never auto-escape read-only mode. It is a session setting, not a privilege boundary.

### §13 — Late / backdated records during a job

- **Variant B (the race), changes after freeze + verification and before deletion (20,147 frozen rows):**

| Row | Outcome |
|---|---|
| New record dated inside the archived range | **Preserved** |
| Backdated record (2021-06-01) | **Preserved** |
| Modified candidate | **Skipped** (still present, counted as drifted) |
| Unchanged verified candidates | **Deleted** (20,146) |

  The job ended `completed_with_exceptions` with reconciliation holding. **The next job's oldest day was 2021-06-01** (the straggler), not boundary + 1, as ADR D-05 intended.
- **How it is achieved:** the delete names only PKs from the verified keys file, and requires `sha256(row::text)` to equal the fingerprint captured in the freeze snapshot. Rows not in the file cannot be addressed; rows changed since the snapshot fail the equality.
- **Variant A, changes between selection and freeze:**
  - **First run failed safely.** Verification refused (V6d: day totals ≠ frozen rows), because selection had been computed before the snapshot. Status `failed`, **0 deleted**.
  - **Fix:** the selection is now recomputed **inside** the freeze snapshot.
  - **After the fix:** the inserted rows are frozen, archived and verified together with their whole days (`ready_for_deletion`). Deleting them later is safe because they are in the verified archive.

## 4. Critical findings (changes to the Phase 2 architecture)

| # | Finding | Evidence | Change to the ADR |
|---|---|---|---|
| F1 | Row fingerprint does not detect rename / type / constraint / FK changes | P8: 5,235 of 5,235 would still match | **Schema+graph hash comparison is mandatory before deletion and before every batch** (ADR assumed fail-closed via fingerprint; partially disproved) |
| F2 | Selection computed before the snapshot disagrees with frozen rows under concurrent inserts | Late-data variant A (first run) | **D-03 refined:** whole-day selection runs *inside* the freeze snapshot; the pre-snapshot selection is a preview only |
| F3 | A consistently re-hashed altered row is caught only by restore + fingerprint | P5 case 4 | **D-13 changed:** V8 is part of the gate on every job (≈ +1 s / 125k rows), not sampled |

| F11 | Parquet with a typical JS mapping is lossy; one npm Parquet package was broken | P4 | Confirms CSV.GZ; Parquet deferred |
| F12 | Batch 10,000 degrades sharply; 2,000 is comfortable | P6 | Default 2,000, hard cap 5,000 (to be re-measured on hosted Nano) |

**Hosted Supabase** (the user chose not to create a throwaway project in this phase; needs an environment that can reach Postgres ports):
